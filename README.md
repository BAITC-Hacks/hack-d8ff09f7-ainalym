**Айналым — финансовая операционная система для торгового бизнеса. Агенты ведут коммерческий цикл. Вы принимаете решения.**
*Ainalym is a financial operations OS for trading businesses. Agents run the commercial cycle. You decide.*

«Айналым» по-казахски — «полный круг». Первая вертикаль — кейс «Автоматический расчёт заказов поставщикам для пополнения склада»: агенты считают, что и сколько заказать у каждого поставщика, по всем источникам данных компании, объясняют каждое число, а утверждает заказ только менеджер по закупу.

## 2. Проблема и для кого

**Для кого.** Менеджер отдела закупа дистрибьютора электротехники (партнёр — ТОО «Электрокомплект», поставщики IEK и System Electric, склад Алматы). Второй пользователь — финансовый руководитель: ему важно, сколько денег заказ заморозит и когда они уйдут поставщику.

**Проблема.** Сейчас потребность считается вручную в Excel, редко и не в реальном времени. Итог — излишки по одним позициям и дефицит по другим одновременно, а разовые крупные продажи (в том числе одному клиенту) раздувают «среднее» и тянут закупку вверх. Пример на данных партнёра — [`docs/FINANCIAL_EXAMPLE.md`](docs/FINANCIAL_EXAMPLE.md) (появляется вместе с документами соавтора).

**Ценность.** Меньше денег в лишнем запасе, меньше дефицита и упущенных продаж, регулярная закупка по объяснимому расчёту.

## 4. Как это работает: от входных данных до результата

Основной сценарий как поток данных:

1. **Данные** — выгрузки партнёра (история продаж по документам, помесячные продажи и остатки, товар в пути, кратность/MOQ, сезонность) → таблицы SQLite (`sales_line`, `sales_month`, `stock_month`, `in_transit`, `sku`, `season_index`).
2. **Расчёт** — менеджер запускает расчёт по поставщику или категории (или новое событие ленты — день продаж, снимок остатков, изменение товара в пути — запускает пересчёт затронутых артикулов агентом). Движок по каждому артикулу: очищает ряд от разовых заказов (M4) → восстанавливает спрос в месяцы без товара (M3) → строит прогноз с сезонностью и ростом (M2) → считает потребность за вычетом остатка и товара в пути (M1).
3. **Рекомендации** — список, сгруппированный по поставщикам, с количеством, срочностью и обоснованием по каждой строке (M5).
4. **Проверка и утверждение** — менеджер корректирует количество (исходная рекомендация сохраняется), утверждает заказ поставщику в очереди решений; утверждение привязано к версии. Автоматической отправки поставщику нет.
5. **Записи** — каждое действие агента и решение человека пишется в журнал (`agent_action`, `approval`); утверждённый заказ создаёт обязательства (предоплата 30 % при утверждении, остаток к сроку поставки).
6. **Результат** — черновик заказа поставщику, файл для 1С (xlsx/csv с колонкой «Код 1с»), подготовленное письмо поставщику (не отправляется), деньги: сколько заморожено по поставщикам и когда уйдут платежи.

### Методика расчёта

Реализация — `computeNeed` в `src/domain/engine.ts` (детерминированно, деньги и количества — `decimal.js`); запуск по поставщику/категории — `runCalculation` в `src/domain/apply.ts`. Параметры — данные поставщика (`src/domain/params.ts`), меняются только утверждаемым предложением. Обозначения: L — срок поставки (IEK 40 дн, SE 50 дн), R — период пересмотра (30 дн).

1. **Источники (M1).** По артикулу читаются: помесячные продажи (`sales_month`), строки документов продаж (`sales_line`), последний известный остаток на начало месяца (`stock_month`, только `known=1`), весь товар в пути (`in_transit`), сезонный индекс поставщика (`season_index`), кратность/MOQ (`sku.moq`). Нет продаж или нет известного остатка → расчёт отказывается и называет недостающий источник (не считает «по нулям»). Категория — фильтр запуска расчёта (`scope.category`).
2. **Регулярный ряд.** Строки документов группируются по (номер документа, месяц); разовые документы исключаются (см. алгоритм ниже); месяц = сумма оставшихся документов (для месяцев без строк — `qty_regular`, иначе `qty_file`).
3. **Упущенный спрос (M3).** Месяцы дефицита (`stockout=1`: остаток на начало = 0 или неизвестен, а в двух из трёх предыдущих месяцев были продажи — разметка `npm run etl`) не входят в базовый спрос: **базовый спрос = среднее по месяцам без дефицита**. Величина компенсации показывается отдельно: Σ max(0, базовый − продажи месяца) по месяцам дефицита (`stockout_uplift`).
4. **Сезонность (M2).** Индекс по календарному месяцу: если у артикула ≥ 12 месяцев без дефицита с продажами — собственный (среднее продаж этого месяца / базовый спрос), иначе индекс поставщика (выручка 2024–2025, нормирована к среднему 1).
5. **Рост (M2).** Рост = продажи последних 6 месяцев / те же 6 месяцев год назад (месяцы дефицита заменены базовым спросом), ограничен ±50 % (множитель 0,5…1,5); если истории не хватает — 1.
6. **Прогноз.** По каждому дню горизонта L + R: базовый спрос × рост × сезонный индекс месяца / 30; сумма — прогноз за горизонт, разбивка по месяцам — `monthly_forecast`.
7. **Страховой запас.** z × σ_мес / √30 × √L, где σ_мес — стандартное отклонение месяцев без дефицита; z = 1,28 при уровне сервиса 90 % (1,645 — 95 %, 2,33 — 99 %).
8. **Потребность (M1).** raw = max(0, прогноз + страховой запас − остаток − товар в пути); рекомендация = raw, округлённая вверх до кратности. Больше товара в пути → меньше рекомендация.
9. **Срочность.** Покрытие = (остаток + в пути) / (базовый спрос × рост / 30) дней: < L → «критично», < L + R → «скоро», иначе «планово»; рекомендация 0 → «не требуется».
10. **Обоснование (M5).** Каждая строка несёт `rationale_ru` с числами («регулярный спрос … шт/мес; сезонность SKU/поставщика, рост ×…; прогноз на … дн … + запас … − остаток … − в пути … = потребность … шт (кратность …); месяцы без остатка: …; исключены разовые документы: …») и `components` со всеми входами и промежуточными числами.
11. **Деньги.** Сумма заказа = Σ количество × себестоимость («СС реал», есть только у SE); при неизвестной себестоимости (IEK) сумма не выдумывается — считается число строк без цены.

### Алгоритм исключения выбросов

1. Единица анализа — документ продажи в месяце: строки одного документа по артикулу суммируются.
2. Порог артикула = max(3 × медиана месячных продаж, 5 × 95-й перцентиль количества в документе, 20 шт). Медиана и p95 берутся из `sku` (считает `npm run etl` по положительным строкам расходных накладных), иначе считаются на лету.
3. Документ с количеством > порога — **разовый крупный заказ**: он не входит в регулярный ряд и попадает в `components.outliers_excluded` (номер, месяц, количество, порог) и в текст обоснования как «исключены разовые документы».
4. Решение по документу можно зафиксировать в `outlier_doc`: `excluded` — исключать всегда, `kept` — вернуть в расчёт (решение менеджера); затем пересчёт.
5. Крупные продажи одному клиенту: в выгрузках партнёра нет идентификатора клиента (только номера документов), поэтому такая продажа ловится на уровне документа тем же правилом.
6. Пример из данных (эталон `oneoff`): IEK `010500008_` ВА47-29 25А — документ `20000099834` на 7 488 шт при p95 строки 144 шт (в 52 раза больше).

Проверка ТЗ п. 4: тест `excludes an injected one-off document from regular demand` добавляет документ на 5 000 шт и проверяет, что регулярная потребность не растёт (`npm run check`).

- сроки поставки и условия оплаты — заявленные политики, не данные партнёра.
