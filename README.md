## 1. Название

**Айналым — финансовая операционная система для торгового бизнеса. Агенты ведут коммерческий цикл. Вы принимаете решения.**
*Ainalym is a financial operations OS for trading businesses. Agents run the commercial cycle. You decide.*

«Айналым» по-казахски — «полный круг». Первая вертикаль — кейс «Автоматический расчёт заказов поставщикам для пополнения склада»: агенты считают, что и сколько заказать у каждого поставщика, по всем источникам данных компании, объясняют каждое число, а утверждает заказ только менеджер по закупу.

## 2. Проблема и для кого

**Для кого.** Менеджер отдела закупа дистрибьютора электротехники (партнёр — ТОО «Электрокомплект», поставщики IEK и System Electric, склад Алматы). Второй пользователь — финансовый руководитель: ему важно, сколько денег заказ заморозит и когда они уйдут поставщику.

**Проблема.** Сейчас потребность считается вручную в Excel, редко и не в реальном времени. Итог — излишки по одним позициям и дефицит по другим одновременно, а разовые крупные продажи (в том числе одному клиенту) раздувают «среднее» и тянут закупку вверх. Пример на данных партнёра — [`docs/FINANCIAL_EXAMPLE.md`](docs/FINANCIAL_EXAMPLE.md) (появляется вместе с документами соавтора).

**Ценность.** Меньше денег в лишнем запасе, меньше дефицита и упущенных продаж, регулярная закупка по объяснимому расчёту.

## 4. Как это работает: от входных данных до результата

Основной сценарий как поток данных:

1. **Данные** — выгрузки партнёра (история продаж по документам, помесячные продажи и остатки, товар в пути, кратность/MOQ, сезонность) → таблицы SQLite (`sales_line`, `sales_month`, `stock_month`, `in_transit`, `sku`, `season_index`).
2. **Расчёт** — менеджер запускает расчёт по поставщику или категории (или новое событие ленты — день продаж, снимок остатков, изменение товара в пути — запускает пересчёт затронутых артикулов агентом). Движок по каждому артикулу: очищает ряд от разовых заказов (M4) → восстанавливает спрос в месяцы без товара (M3) → строит прогноз с сезонностью и ростом (M2) → считает потребность за вычетом остатка и товара в пути (M1).
3. **Рекомендации** — список, сгруппированный по поставщикам, с количеством, срочностью и обоснованием по каждой строке (M5).
4. **Проверка и утверждение** — менеджер корректирует количество (исходная рекомендация сохраняется), утверждает заказ поставщику в очереди решений; утверждение привязано к версии. Автоматической отправки поставщику нет.
5. **Записи** — каждое действие агента и решение человека пишется в журнал (`agent_action`, `approval`); утверждённый заказ создаёт обязательства (предоплата 30 % при утверждении, остаток к сроку поставки).
6. **Результат** — черновик заказа поставщику, файл для 1С (xlsx/csv с колонкой «Код 1с»), подготовленное письмо поставщику (не отправляется), деньги: сколько заморожено по поставщикам и когда уйдут платежи.

### Методика расчёта

Методика задана контрактом (`docs/CONTRACTS.md` §1, `docs/PRODUCT.md`); реализация — `src/domain/engine.ts` (статус — `docs/TASK_MAP.md`). Параметры — данные, а не код; меняются через `/api/params` только утверждаемым предложением.

- **Горизонт** = срок поставки L + период пересмотра R. Политика: L(IEK) = 40 дней, L(SE) = 50 дней, R = 30 дней.
- **Базовый спрос** — по «регулярному» месячному ряду артикула: продажи без исключённых разовых документов (M4), с восстановленными месяцами дефицита (M3).
- **Сезонность (M2)** — собственный сезонный индекс артикула, если у него ≥ 12 месяцев с продажами; иначе индекс поставщика из файлов «Сезонность …»: выручка 2024–2025 по календарным месяцам, нормированная к среднему 1 (неполный 2026 год исключён). Прогноз на месяц m = базовый спрос × индекс(m) × (1 + рост).
- **Рост (M2)** — рост год к году по регулярному ряду, ограничен ±50 %.
- **Упущенный спрос (M3)** — месяц считается месяцем дефицита, если остаток на начало месяца = 0 или неизвестен, а в двух из трёх предыдущих месяцев были продажи (так размечает `npm run etl`: 1 596 таких месяцев). Продажи такого месяца занижены; спрос оценивается по соседним месяцам. Показываются обе цифры: по «сырым» продажам и скорректированная.
- **Потребность (M1)** = прогноз за горизонт − свободный остаток − товар в пути + страховой запас (уровень сервиса 90 %, z = 1,28), не меньше нуля, с округлением вверх до кратности/MOQ. Изменение любого источника (например, товара в пути) меняет результат.
- **Категория** — «Категория 2026» из выгрузки SE; для IEK — первые 4 символа кода 1С. Расчёт можно запустить по категории.
- **Деньги** — сумма заказа = Σ количество × себестоимость («СС реал», известна только для SE); для IEK показывается «себестоимость не задана», а не ноль.

### Алгоритм исключения выбросов

1. Единица анализа — строка документа продажи (номер документа, дата, количество), а не месяц.
2. Для каждого артикула считаются медиана месячных продаж и 95-й перцентиль количества в одном документе.
3. Строка документа считается **разовым крупным заказом**, если её количество > max(3 × медиана месячных продаж, 5 × p95 количества в документе, 20 шт).
4. Такая строка исключается из регулярного ряда (`sales_month.qty_regular`) и записывается в `outlier_doc` с правилом и статистикой; в обосновании рекомендации она показана как «исключено».
5. Пограничные случаи могут уйти на типизированное решение (Jev/OpenAI) или менеджеру (`outlier_review`); в режиме «Правила без LLM» правило детерминировано. Менеджер может вернуть документ в расчёт — это новое предложение и пересчёт.
6. Крупные продажи одному клиенту: в выгрузках партнёра нет идентификатора клиента (только номера документов), поэтому одна крупная продажа ловится на уровне документа тем же правилом.

Проверка (ТЗ, пункт 4): разовый документ на 5 000 шт, добавленный через ленту событий, меняет регулярное количество меньше чем на 10 %, а документ виден как «исключено» (статус — `docs/TASK_MAP.md`).
