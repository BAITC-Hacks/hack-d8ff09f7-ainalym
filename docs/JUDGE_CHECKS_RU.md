# Пять обязательных проверок ТЗ — пошагово для проверяющего

Автор: Маулен (соучредитель). Каждая проверка ТЗ (раздел 7, must have 1–5) — какой артикул взять, что сделать и что должно получиться. Артикулы — эталонные из `tests/fixtures/eval/replenishment_expectations.json`, выбраны по данным партнёра (`npm run etl`). Какие шаги уже можно пройти в текущей версии, с временем проверки, — в `docs/TASK_MAP.md`; автоматические проверки — `npm run check`.

Подготовка — как в README, раздел 7: `npm install` → `cp .env.example .env.local` → в `.env.local` указать `DATABASE_PATH=./data/partner.db` → `npm run etl` → `npm run dev`. Ключи не нужны: режим «Правила без LLM». Затем «Закупки» → «Запустить расчёт» по SE и по IEK: без расчёта у артикулов ещё нет рекомендации.

## 1. Потребность считается по всем источникам

- **Артикул, где изменение видно на экране:** `300200745_` — розетка 2-я IP54 Alas Profi 54 белая (SE): свободный остаток 23 шт, в пути 120 шт.
- **Действие:** после расчёта по SE открыть карточку артикула: рекомендация **126 шт**, «скоро», в обосновании «− остаток 23 − в пути 120». В ленте событий ввести «Товар в пути +100» по этому коду.
- **Ожидается:** событие подписано «Симулятор мира — синтетическое событие»; агент пересчитывает только этот артикул; рекомендация **24 шт**, в обосновании «− в пути 220»; в журнале карточки — «Пересчитана потребность 300200745_: 24 шт».
- **Эталон для автопроверки:** `010500006_` (ВА47-29 16А IEK, в пути 30 000 шт) — потребность до округления уменьшается ровно на 100 (строка M1 в `node scripts/scenario.mjs`); заказ там 0 и до, и после, потому что запаса хватает.
- **Вторая часть:** если убрать обязательный источник (например, остатки), расчёт отказывается и называет недостающий источник, а не считает «по нулям» (строка M1-source).

## 2. Сезонность и рост

- **Артикул:** `130300027_` — сжим У 733M (SE); 24 месяца продаж в 2024–2025, пик в III квартале обоих лет.
- **Действие:** открыть карточку артикула, посмотреть прогноз по месяцам.
- **Ожидается:** прогноз по месяцам разный, а не одно среднее: максимум/минимум по месяцам ≥ 1,3; в обосновании указан источник сезонности (артикул или поставщик) и множитель роста.

## 3. Упущенный спрос в период отсутствия товара

- **Артикул:** `130200032_` — розетка на DIN-рейку РАр10-3-ОП IEK; восемь месяцев дефицита в 2025–2026 после продаж.
- **Действие:** открыть карточку, посмотреть отмеченные месяцы без товара.
- **Ожидается:** месяцы дефицита перечислены в обосновании («Без продаж из-за отсутствия остатка: …»); потребность с поправкой **больше**, чем по «сырым» продажам.

## 4. Разовый крупный заказ не раздувает регулярную потребность

- **Артикул:** `010500008_` — автомат ВА47-29 (1ф) 25А IEK; в истории есть документ `20000099834` на 7 488 шт при обычном документе до 144 шт.
- **Действие:** в ленте событий выбрать пресет «Добавьте разовый документ на 5000 шт. за прошлый месяц и покажите исключение» (`JUDGE-ONEOFF-5000`), пересчитать.
- **Ожидается:** регулярное количество изменилось меньше чем на 10 %; документ `JUDGE-ONEOFF-5000` показан в обосновании как исключённый.

## 5. Итоговый список по поставщикам с обоснованием

- **Действие:** экран рекомендаций после расчёта по обоим поставщикам.
- **Ожидается:** строки сгруппированы по IEK и SE; у каждой строки есть поставщик и непустое обоснование с числами (регулярный спрос, сезонность, рост, прогноз, запас, остаток, в пути, кратность); экспорт открывается как таблица с колонкой «Код 1с».
- **Дополнительно:** `200400085_` (кабель F/UTP, IEK) — себестоимость неизвестна: в сумме заказа он не превращается в 0 KZT, а считается строкой «себестоимость не задана».

## Чего не должно случиться ни в одной проверке

- заказ не уходит поставщику сам — только черновик после утверждения человеком;
- синтетическое событие жюри подписано «Симулятор мира — синтетическое событие»;
- при недоступном AI результат помечен «Провайдер недоступен» или «Правила без LLM», а не выдан за живой ответ.
